CONTINUITY MOTORS — FINAL WEBSITE FUNCTIONALITY & TECHNICAL ARCHITECTURE
Version 2.0
Updated after SEO/AI content architecture work
Date: October 2026

PURPOSE
This is the implementation specification for the first Continuity Motors website.
It combines:
- front-end architecture
- Cloudflare backend architecture
- first-party experiment tracking
- GA4
- Microsoft Clarity
- Cloudflare D1
- Turnstile
- SEO/search readiness
- AI/LLM readability
- content architecture
- accessibility
- performance
- privacy/consent

The site has two equal jobs:
1. Look and behave like a credible premium motorcycle brand.
2. Generate trustworthy experiment evidence about Camel and Messerschmitt.

11. API ROUTES
==================================================

POST /api/session
Purpose:
- create session
- record landing context
- record experiment assignment
- record consent state
- record campaign fields

POST /api/events
Purpose:
- receive batched meaningful experiment events

Recommended rules:
- max 25 events/request
- event-name allowlist
- strict request validation
- server timestamp added
- reject oversized payloads
- no PII in metadata_json
- rate-limit abnormal traffic

POST /api/lead
Flow:
1. validate request
2. verify Turnstile server-side
3. normalize email
4. rate-limit
5. deduplicate as desired
6. insert lead
7. insert conversion in the same server flow
8. return success

GET /api/experiment
Purpose:
- return session experiment assignment where needed

17. PRIMARY EXPERIMENT METRICS
==================================================

Product View Rate
= product viewers / qualified sessions

Qualified Product View
initial proposed definition:
product_active_ms >= 15,000
AND max_scroll_pct >= 50

Keep threshold versioned.

Deep Technical Interest
= technical interaction OR engineering active-time threshold

Switch-Away Rate
= sessions switching from product A to product B / sessions exposed to A

Switch-Back Rate
= A -> B -> A sessions / A -> B switchers

CTA Intent Rate
= sessions with CTA click / qualified product viewers

Lead Conversion Rate
= successful leads / qualified product viewers

Share Rate
= sessions with share click / qualified product viewers

Technical-to-Lead
= leads after technical interaction / sessions with technical interaction

DO NOT collapse all outcomes into one arbitrary winner score.

Keep separate:
attention
depth
technical curiosity
comparative behavior
CTA intent
lead conversion
sharing
return behavior

27. DATA FLOW — FIRST VISIT
==================================================

1. Read consent state.
2. Create session_id.
3. Parse UTM/referrer.
4. Determine experiment assignment.
5. POST /api/session.
6. Render content.
7. Activate GA4/Clarity according to consent.
8. Queue meaningful first-party events.
9. Batch POST /api/events.
10. Flush section/session summaries on page hide/route change.

==================================================
28. DATA FLOW — LEAD
==================================================

1. User focuses/interacts with form.
2. record lead_form_start.
3. user submits.
4. Turnstile token sent with email to Worker.
5. Worker verifies Turnstile.
6. normalize email.
7. rate-limit.
8. D1 inserts lead.
9. D1 inserts conversion.
10. server returns success.
11. browser shows success UI.
12. GA4/Clarity receive allowed non-PII success event.

D1 server-side conversion is the source of truth.
Do not treat a client-side analytics success call as the canonical lead record.

31. EXPERIMENT INTEGRITY RULES
==================================================

1. Keep product pages structurally equivalent.
2. Do not quietly change one page mid-test.
3. Version meaningful copy/image changes.
4. Record experiment_version with events.
5. Keep UTM campaign traffic distinguishable.
6. Randomize product order for neutral traffic.
7. Separate randomized traffic from direct-product traffic.
8. Use the same CTA language/prominence on both product pages during a comparison test.
9. Do not give one product validated specifications while the other lacks equivalent information during the same comparison.
10. Check page performance before interpreting product-interest differences.
11. Mark internal/test traffic so it can be excluded.
